# 产品定位与场景规划

记录目标用户场景的判断依据,避免功能规划时凭空造需求或漏掉真实需求。随判断变化持续更新,不是一次性快照。

## 目标场景:办公/专业场景,而非学习场景

不面向"学生自学一本教材"这类学习场景做优化,面向"专业人士处理一批项目材料"这类办公场景。三个候选方向:

- **法律案件准备**(律师/律所):案卷/证据材料 + 庭审/询问录音
- **投资尽调**(分析师):财报/招股书 + 管理层访谈录音
- **临床病例复核**(医生/护士):用药规范文档 + 查房/病例讨论录音

三者共性,也是筛选标准:
- 项目制、一次性语料库,用完可归档,不需要持续同步/连接器
- 文档 + 录音天然共存,能用上音频转录这条现有能力
- 答错代价真实存在(执业风险/决策金额/生命安全),不是"答错了尴尬一下"
- 离线是硬要求而非偏好(保密特权/内幕信息/病人隐私)
- 个人/小团队工具,不需要多用户权限模型

## 不做整个企业级知识库平台

多用户、跨数据源持续同步、权限隔离这条路不走,原因是结构性冲突,不只是"暂时没空":

- GPU 互斥锁/`ImportQueue` 是全局单工作线程设计,假设同一时刻只有一个任务在跑,跟企业级并发多用户直接冲突
- `book_id` 单 collection、检索不跨库(见 `docs/book-management.md`),跟"企业整体知识库"要的跨海量文档统一检索方向相反
- 没有权限模型、没有 connector,补齐这些是另一个产品的工作量
- 会跟 RAGFlow(85k star)、Dify(149k star)这类有正经公司全职团队运营的项目正面竞争,现阶段打不过
- 消费级 PC / 离线 / 基于 Ollama 是任务书 A 的硬性交付形态,不是可选项

## 功能不按场景纵向定制,按通用机制横向复用

三个方向真正需要新建的是通用机制,不是三套代码,场景差异体现在配的语料和参数上:

- **跨来源一致性核对**:给定两段检索到的内容判断是否语义冲突,机制跟内容是证词、访谈还是查房记录无关
- **参数化结构化抽取**:模型按用户这次问的字段动态抽取(金额/日期/条款/剂量),不预设某个领域专属 schema
- **拒答严格度配置**:在 issue #40 的相关性阈值机制上加一档"严格程度",临床场景调高,其余场景默认

## 各方向的语料与验证

| 方向 | 语料 | 权重最高的通用能力 | 验证方式 |
|---|---|---|---|
| 法律案件准备 | 案卷/证据材料 + 庭审/询问录音 | 跨来源核对 + 引用精确到条款/页码 | 复用 CS testset 方法论出题,专考引用精确度;语料复用已选定的 Criminal Procedure |
| 投资尽调 | 财报/招股书 + 管理层访谈录音 | 参数化抽取 + 跨来源核对 | 找公开财报 + 模拟电话会议录音出题,验证抽取准确率 |
| 临床病例复核 | 用药规范文档 + 查房/病例讨论录音 | 拒答严格度 + 精确引用 | 语料复用已选定的 Nursing Pharmacology,现成度最高 |

候选书目见 `eval/parser_selection/textbook-candidates.md`。

## CS/OSTEP 语料的角色:基准测试集,不是目标场景

CS 学科的真实办公用途有限——软件工程师日常工作基本不会翻回去查操作系统原理教材,真实用处基本只在"学习/备考"。CS 语料的价值不在于代表一个目标用户场景,而在于它是目前唯一有 ground-truth 核验 + 真实幻觉率数据的完整评测(60 题 QA,`eval/testset/cs/`,issue #40 就是靠它挖出来的)。继续把它当管线质量的基准测试集使用(验证 #17/#40/#11/#10 修复前后的 Hit@5/幻觉率对比),不用于对外的场景定位叙事。
